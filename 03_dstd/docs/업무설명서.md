# 잘 읽었다면 확인되는 것
주문 파일의 한 행은 무엇입니까?
AMT와 unitPrice는 왜 다른지

## 1. 상황

한빛유통은 생활용품을 온라인으로 판매합니다. 데이터가 세 시스템에 흩어져 있습니다.

| 시스템 | 구축 | 현재 상태 | 내보낸 파일 |
|---|---|---|---|
| 회원관리 시스템 | 2019년 | 운영 중. 최초 구축 담당자 퇴사 | `cust_master.csv` |
| 구 주문관리 시스템 | 2020년 | 유지보수 종료. 조회만 가능 | `order_2026.csv` |
| 신 상품 시스템 | 2025년 | 운영 중. REST API 제공 | `product_api_response.json` |

마케팅팀이 다음을 요청했습니다.

> "고객별로 최근에 언제 샀고, 몇 번 샀고, 얼마나 썼는지 알고 싶습니다.
>  다음 달에 누가 또 살지 예측해 보려고 합니다."

문제는 세 시스템의 고객번호, 상품코드, 상태값 표기가 서로 다르다는 것입니다.
이 프로젝트의 목표는 **세 원천을 하나의 표준으로 통합하고, 그 결과를 다른 사람이
재사용할 수 있게 전달하는 것**입니다.

## 2. 반드시 알아야 할 업무 규칙

값만 보고 추측하지 마십시오. 아래가 확정된 업무 규칙입니다.

### 2.1 고객 식별자의 적용 범위

- `CUST_NO`는 **회원가입한 고객에게만** 부여됩니다. 7자리 숫자 문자열이며 **선행 0이 있습니다**(`0000123`).
- 비회원도 주문할 수 있습니다. 이 경우 주문 파일의 고객 식별자가 **공란이거나 `GUEST`** 입니다.
- 비회원 주문은 **매출에는 포함되지만, 고객별 구매 특성 집계에서는 제외**합니다.
  같은 사람이 여러 번 비회원으로 샀는지 알 방법이 없기 때문입니다.
- 탈퇴 회원(`DEL_YN = 'Y'`)의 **주문 이력은 보존**합니다. 다만 마케팅 대상에서는 제외합니다.
  탈퇴는 오류가 아니라 정상 상태입니다.

### 2.2 주문 데이터 한 행의 의미

- 주문 파일의 **한 행은 주문 항목(order item)** 입니다. 주문 한 건이 아닙니다.
- 식별자는 **`ORD_NO` + `ORD_SEQ` 복합키**입니다. 한 주문에 상품이 세 개면 세 행입니다.
- 따라서 행 수를 세면 "주문 건수"가 아니라 "주문 항목 수"가 나옵니다.

### 2.3 금액의 의미

- `AMT`는 **해당 항목의 실판매 금액**입니다. 정가 × 수량에서 할인을 적용한 뒤의 금액입니다.
- 상품 마스터의 `unitPrice`는 **정가**입니다.
- 그러므로 **`AMT ÷ QTY` 와 `unitPrice` 가 다른 것은 정상**입니다. 오류로 처리하지 마십시오.
- 금액은 원 단위 정수입니다. 다만 내보내기 과정에서 표기가 섞였습니다(2.7 참조).

### 2.4 배송비

- `DLV_FEE`는 **주문 한 건에 부과되는 값**입니다.
- 그런데 구 주문관리 시스템은 이 값을 **주문의 모든 항목 행에 똑같이 반복 기재**합니다.
- 항목 행 단위로 배송비를 합산하면 **항목 수만큼 부풀려집니다.**
- 이 구조 때문에 TO-BE 모델에서는 **주문 헤더와 주문 항목을 분리**해야 합니다.
  주문 단위 속성(주문일, 고객, 결제수단, 배송비, 주문상태)은 헤더로,
  항목 단위 속성(상품, 수량, 금액)은 항목으로 갑니다.

### 2.5 통화와 금액 단위

- 기본 통화는 **KRW**, 원 단위 정수입니다.
- 신 상품 시스템에 **해외 직수입 상품이 외화로 등록**되어 있습니다.
- 환산은 **고정 환율**을 사용합니다. 실시간 환율을 조회하지 마십시오.
  - **USD 1 = 1,350원**
  - **JPY 1 = 9.2원**
- 환산한 금액에는 **환산 여부를 별도 컬럼에 기록**하십시오. 원본을 덮어쓰지 마십시오.

### 2.6 상태 코드

업무 상태는 여섯 개입니다. 이것이 표준입니다.

| 표준 코드 | 표준 코드명 | 의미 |
|---|---|---|
| `RECEIVED` | 접수 | 주문이 접수되었으나 결제 전 |
| `PAID` | 결제완료 | 결제가 완료됨 |
| `SHIPPING` | 배송중 | 출고되어 배송 중 |
| `DELIVERED` | 배송완료 | 고객 수령 완료 |
| `CANCELED` | 취소 | 배송 전 주문 취소 |
| `REFUNDED` | 환불 | 배송 후 반품·환불 |

구 주문관리 시스템의 `ORD_ST`에는 이 여섯 상태가 **여러 표기로 섞여** 저장되어 있습니다.
숫자 코드, 영문 약어, 한글이 뒤섞였습니다. 매핑은 여러분이 표준 코드 정의서로 작성합니다.

**위 여섯 개에 해당하지 않는 값이 나오면 추측해서 매핑하지 마십시오.**
격리하고 '담당자 확인 필요' 목록에 올리십시오.

### 2.7 취소와 환불의 처리 기준

- `CANCEL_DT`에 값이 있으면 취소 또는 환불입니다.
- 취소·환불 건은 **고객별 구매 특성 집계에서 제외**합니다.
- 그러나 **원천 데이터에서 삭제하지 않습니다.** 제외 건수와 금액을 처리 내역에 남기십시오.

### 2.8 기준 시점

- 이 프로젝트의 **기준일은 2026-06-30** 입니다.
- 모든 집계는 `ORD_DT` 기준으로 **2026-06-30까지**만 사용합니다.
- 주문 파일에는 **2026년 7월 데이터도 포함되어 있습니다.** 이것은 실수가 아닙니다.
  - **관측 기간: 2026-01-01 ~ 2026-06-30** → 고객 특성을 만드는 데 사용
  - **정답 기간: 2026-07-01 ~ 2026-07-31** → "다음 달에 샀는가"를 표시하는 데만 사용
  - 관측 기간 특성에 7월 데이터를 섞으면 **데이터 누수**입니다.

### 2.9 날짜 표기

구 시스템은 배치 작업마다 날짜 형식이 달랐습니다. 네 가지가 섞여 있습니다.

| 형식 | 예 |
|---|---|
| ISO | `2026-03-15` |
| 슬래시 | `2026/03/15` |
| 붙임 | `20260315` |
| 일-월-년 | `15-03-2026` |

마지막 형식은 **일이 먼저 옵니다.** `15-03-2026`은 3월 15일입니다.
`03-15-2026` 같은 월-일-년 형식은 사용하지 않습니다.

**존재하지 않는 날짜**(예: 2월 30일)가 들어 있을 수 있습니다.
임의로 보정하지 말고 격리하십시오.

## 3. 코드 정의

### 3.1 회원 등급 `GRD_CD`

| 코드 | 의미 |
|---|---|
| `G01` | 일반 |
| `G02` | 실버 |
| `G03` | 골드 |
| `G04` | VIP |

### 3.2 결제 수단 `PAY_MTHD`

| 코드 | 의미 |
|---|---|
| `CARD` | 신용카드 |
| `BANK` | 계좌이체 |
| `VBANK` | 가상계좌 |
| `MOBILE` | 휴대폰 결제 |

`ETC`라는 값이 나올 수 있습니다. 이 값의 의미는 **정보시스템팀도 확인하지 못했습니다.**
격리하지는 말고, '확인필요'로 표시해 집계에서 구분하십시오.

### 3.3 과세 구분 `taxType`

| 코드 | 의미 |
|---|---|
| `TAX` | 과세 |
| `FREE` | 면세 |

`Z`라는 값이 나올 수 있습니다. 정의가 없습니다. 격리하고 확인 목록에 올리십시오.

### 3.4 삭제 구분 `DEL_YN`, 사용 여부 `useYn`

`Y` / `N`. `DEL_YN = 'Y'`는 탈퇴 회원, `useYn = 'N'`은 판매 중지 상품입니다.
둘 다 오류가 아닙니다. 과거 주문과 연결되므로 삭제하지 마십시오.

## 4. 인수인계 메모 (전임 담당자 노트 발췌)

> - 회원 파일은 예전 시스템이라 **EUC-KR**로 떨어집니다. UTF-8로 열면 깨집니다.
> - 주문 파일은 **UTF-8인데 앞에 BOM이 붙습니다.** 도구에 따라 첫 컬럼명을 못 읽습니다.
> - 고객번호와 상품코드는 **숫자처럼 보이지만 문자열**입니다. 앞의 0이 의미가 있습니다.
>   엑셀에서 열었다가 저장하면 0이 날아갑니다. 조심하십시오.
> - 주문 파일에 **같은 행이 두 번 들어간 경우**가 있습니다. 배치 재실행 사고였습니다.
>   대부분은 완전히 같지만, **금액만 다른 경우**도 몇 건 있습니다. 어느 쪽이 맞는지 모릅니다.
> - 고객·상품 마스터에 **없는 코드가 주문에 들어간 건**이 있습니다.
>   구 시스템이 참조 검사를 하지 않았습니다.
> - 주문일·배송비 같은 **주문 단위 값이 항목마다 다른 주문**이 몇 건 있습니다.
>   배치가 중간에 끊겼다 다시 돈 것으로 보이는데 확인하지 못했습니다.
>   이런 주문은 어느 값이 맞는지 알 수 없습니다.

- 한 행 = 고객 한 명 (회원만)

- 취소·환불 건 제외, 비회원 제외

## 6. 팀별 추가 안내

팀마다 내보낸 시점과 시스템 설정이 달라 **컬럼 이름과 코드 체계가 다릅니다.**
아래는 팀별로 다른 부분입니다. 나머지 업무 규칙은 모두 동일합니다.

| | 공통(수업용) | 팀 A | 팀 B | 팀 C |
|---|---|---|---|---|
| 주문 파일의 고객 식별자 컬럼 | `CUSTNO` | `MEM_ID` | `MEM_NO` | `CUST_ID_OLD` |
| 주문 파일의 상품 식별자 컬럼 | `GOODS_CD` | `ITEM_NO` | `ITEM_CD` | `PRD_CODE` |
| `ORD_ST` 표기 체계 | 숫자·영문·한글 혼재 | 숫자 중심 | 영문 약어 중심 | 한글 중심 |
| 외화 상품 | USD | USD | 없음 | USD, JPY |
| 금액 단위 특이사항 | 없음 | 없음 | **침구 카테고리 단가는 천원 단위로 등록됨** | 없음 |
| 정의 없는 상태 코드 값 | `99` | `88` | `UNKN` | `확인불가` |

> **팀 B 주의.** 침구 카테고리 상품의 `unitPrice`는 구 시스템이 **천원 단위**로 등록했습니다.
> 예를 들어 `12.9`는 12,900원입니다. 주문 파일의 `AMT`는 원 단위 그대로입니다.
> 따라서 이 카테고리만 `AMT ÷ QTY`가 `unitPrice`의 약 1,000배로 보입니다.
> 단가를 원 단위로 통일한 뒤 검증하십시오.

## 7. 하지 말아야 할 것

- 판단이 서지 않는 값을 **삭제하는 것**. 격리하고 기록하십시오.
- 결측값을 **임의로 채우는 것**. 채웠다면 무엇을 어떤 근거로 채웠는지 남기십시오.
- 잘못된 날짜를 **그럴듯한 날짜로 고치는 것**.
- 정의에 없는 코드를 **비슷해 보이는 표준 코드에 매핑하는 것**.
- 컬럼 이름만 바꾸고 **표준화가 끝났다고 하는 것**.
- 주문 단위 속성이 항목마다 다른 주문을 **아무 값이나 골라 헤더로 만드는 것**.
- 오류 0건이라고 **보고하는 것**. 남은 문제와 그 이유를 적는 것이 더 정확한 보고입니다.

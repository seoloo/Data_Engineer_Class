## STEP 15 — CSV와 Parquet 저장 · 저장 모드 · 폴더 파티셔닝

- 같은 `clean`을 CSV와 Parquet로 저장하고 다시 읽어 스키마와 건수, 폴더 크기를 비교했다. `write`에 전달한 경로는 결과 폴더이며, 그 안에 `part-...` 데이터 파일과 `_SUCCESS` 같은 관리 파일이 생긴다.
- CSV는 자료형을 파일에 함께 기록하지 않는다. 현재 코드처럼 `header=True`만 주어 다시 읽으면 시각·요금까지 문자열로 읽힌다. Parquet는 저장된 스키마를 이용해 `tag_time`을 Timestamp, `fare`를 Integer로 다시 읽는다.
- Parquet는 열 중심 저장과 압축을 지원한다. `du()`는 결과 폴더의 파일 크기를 합산한다. 파일 수·압축·데이터 내용에 따라 크기가 달라지므로 정답 예시의 KB 값을 내 측정값으로 간주하지 않는다.
- 기본 저장 모드는 같은 경로가 있으면 오류를 낸다. `append`는 기존 데이터와 겹치는지 검사하지 않고 추가하므로 같은 데이터를 다시 쓰면 중복된다. `overwrite`는 해당 결과를 대체한다.
- `partitionBy("tag_type")`는 `tag_type=IN`, `tag_type=OUT`처럼 값별 하위 폴더를 만든다. `partitionBy("tag_type", "hh")`는 승하차 폴더 아래 시간 폴더를 만드는 두 단계 분할이다.
- `repartition()`·`coalesce()`는 실행 중 데이터 조각을 조절하고, `write.partitionBy()`는 저장 폴더의 분할 기준을 정한다. 이 실습의 `coalesce(1)`은 데이터를 한 실행 파티션으로 모은 뒤 시간별 폴더에 쓰는 방식이다.
- 폴더를 나눈 뒤 `tag_type == "OUT"`으로 읽으면 실행 계획의 `PartitionFilters`에서 조건을 확인한다. 필요한 폴더만 읽도록 범위를 줄이는 파티션 가지치기와 연결된다. 지나치게 많은 값으로 폴더를 나누면 작은 파일이 많아질 수 있다.

정답 파일의 비교 기준:

| 확인 항목 | 기대값 |
|---|---|
| 정상 데이터 Parquet 저장 후 행 수 | 1,978행 |
| 같은 데이터를 한 번 append한 뒤 | 3,956행 |
| 정상 데이터로 overwrite한 뒤 | 1,978행 |
| `by_type`에서 하차만 읽은 결과 | 986행 |

## STEP 16 — Delta Lake와 Bronze 원문 보존

- Delta 확장과 카탈로그 설정을 추가하고 `configure_spark_with_delta_pip()`로 SparkSession을 준비했다. `spark.jars.ivy`는 필요한 라이브러리를 내려받는 로컬 캐시 경로다.
- Delta 테이블에는 Parquet 데이터 파일과 `_delta_log` 장부가 있다. `.write.format("delta").save(...)`로 쓰고 `.read.format("delta").load(...)`로 장부를 해석해 읽는다.
- Bronze에는 `RAW_SCHEMA`로 읽은 `raw_text`를 저장한다. 시각도 문자열로 남겨 `07:67:00`처럼 잘못된 값의 원문을 보존한다. Timestamp로 먼저 바꾸면 변환 실패 값이 NULL이 되어 원래 표기를 잃을 수 있다.
- 장부의 첫 JSON에서 `commitInfo`(작업 정보), `metaData`(스키마 등), `protocol`(읽기·쓰기 규약), `add`(추가한 데이터 파일) 기록을 확인하는 코드를 작성했다.
- `DeltaTable.forPath()`로 테이블을 지정하고 `history()`에서 버전과 작업 종류를 본다. 작은 로그를 `append`한 후 `versionAsOf`로 버전 0과 1을 각각 읽어 과거 상태를 비교한다.
- `delete("event_id LIKE 'M%'")`로 연습용 사건을 삭제하고 과거 버전도 읽는 흐름을 실습했다. 현재 상태에서 삭제한 것과 보존 중인 과거 버전을 읽는 것은 구분된다. 과거 조회는 필요한 장부와 데이터 파일이 남아 있는 범위에서 가능하다.

### 실제 원본 장부에서 확인한 반복 실행

`C:\sparkcamp\lake\bronze\tags\_delta_log`에 버전 0~4의 JSON이 있고, 작업 메타데이터는 다음과 같다. 행 수는 각 커밋의 출력·삭제 지표이며 전체 테이블을 이번에 조회한 결과가 아니다.

| 버전 | 작업 | 장부의 행 수 지표 |
|---|---|---|
| 0 | WRITE / Overwrite | 2,008행 출력 |
| 1 | WRITE / Append | 12행 출력 |

- 따라서 삭제 작업이 정답 예시의 버전 2가 아니라 내 장부의 버전 4에 있는 것은 실행 횟수 차이로 설명된다. `versionAsOf`에는 각 버전에 어떤 작업이 있었는지 확인한 뒤 번호를 넣는다.

## STEP 20 — 종합 문제 일부 복습

- **H-1:** 정상 하차 이벤트에 역 마스터를 붙여 역 이름별로 세고 상위 세 역을 표시했다. `filter → join → groupBy → count → orderBy → show`를 연결하는 복습이다.
- **H-2:** 승차이면서 07:00 이상 08:00 미만인 태그를 셌다. 시간 조건을 시작 포함·끝 제외로 작성했다.
- **H-6:** 승차를 카드별로 센 뒤 2회 이상인 그룹만 남기고, 마지막 `count()`로 해당 카드 수를 구했다. 첫 `groupBy().count()`는 카드별 횟수 표, 마지막 `count()`는 조건을 만족하는 그룹 수다.
- **H-7:** 격리 사유별 건수를 구하고 `원본 = 중복 + 격리 + 정상`을 출력했다. STEP 13의 품질 분류와 건수 보존을 다시 적용했다.
- 준비 셀의 `to_trips(clean)`은 모든 정상 이벤트를 `trip_id`로 묶어 이동 표를 만든다. 정답에서는 1,000행으로, STEP 13의 승차 기준 left join 결과 992행과 다르다. 정상 승차가 없는 하차 8건도 이 그룹 집계에는 포함되기 때문이다.

## 복습 포인트 (내 코드에서)

- **15-6 — 미작성:** 기존 Parquet 경로에 다시 썼을 때의 `PATH_ALREADY_EXISTS` 오류를 확인하는 셀이 비어 있다. 기존 결과를 지우는 초기화 셀과 구분해서 실행한다.
- **15-9 — 저장문 주석 처리:** `by_type`를 만드는 줄이 주석이다. 현재 원본에는 해당 결과 폴더가 있지만, 초기화로 `out/s15`를 비운 뒤에는 이 코드 그대로 폴더 조회와 15-10 읽기를 재현할 수 없다. 새로 시작할 때 저장 단계가 실행되는지 확인한다.
- **15-7 — append 반복:** append는 중복을 자동 제거하지 않는다. 셀을 여러 번 실행하면 정답의 두 배 건수보다 더 늘어날 수 있다.
- **16-3 — 파일 인코딩:** 현재 `open(...)`에는 `encoding`이 없다. JSON 장부는 `encoding="utf-8"`로 읽도록 명시하면 Windows 기본 인코딩에 따른 문제를 줄일 수 있다.
- **16-8 — 건수 출력 누락:** 삭제 뒤 `print(spark.read.format("delta").load(...))`로 DataFrame 객체를 출력하고 있다. 삭제 후 행 수를 확인하려면 `.count()`가 필요하다. 실제 삭제가 커밋된 사실은 위 장부의 DELETE 기록에서 확인했다.
- **16-10~16-12 — 미작성:** 역 마스터 UPDATE, 스키마가 다른 데이터 추가 시도, `isDeltaTable()` 확인 셀이 남아 있다.
- **H-3·H-4·H-5·H-8·H-9·H-10 — 미작성:** 노선별 승차, 30분 초과 이동, 15분 피크 창, 출발·도착역 쌍, 노선별 평균 요금, 결과 Parquet 저장을 추가로 풀어야 한다.
- **H-8과 H-10의 연결:** H-8은 상위 세 행을 화면에 보지만 `top_routes` 변수 자체는 모든 역 쌍 집계다. 정답의 H-10은 그 전체 표를 저장하므로 기대 행 수가 3이 아니라 56이다.

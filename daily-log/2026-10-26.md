## STEP 02 — Docker로 Kafka 준비 · Python 연결

- [kafka1.yml](../05_kafkacamp/kafka1.yml)은 Kafka 브로커 한 대를 실행하는 Docker Compose 구성이다. PC의 `localhost:9092`와 컨테이너의 Kafka 포트를 연결한다.
- PowerShell에서 컨테이너 실행·상태·로그를 확인하는 흐름과, `docker exec -it kafka bash`로 컨테이너 안 터미널에 들어가는 흐름을 구분한다. 각 문제의 `[어디서]`를 먼저 확인한다.
- `AdminClient({"bootstrap.servers": BOOT})`를 만들고 `list_topics(timeout=5)`로 메타데이터를 요청한다. 이 응답에는 브로커·토픽·파티션 정보와 클러스터 ID가 포함된다.
- 작성된 02-5에서는 `.cluster_id`를 확인했다. 02-6 토픽 목록 조회와 02-7 잘못된 주소 연결 실험은 코드가 비어 있다.

## STEP 03 — 토픽에 메시지 보내고 읽기

- 토픽을 생성하고 목록·상세 정보를 확인한 뒤 콘솔 프로듀서로 전송하고 콘솔 컨슈머로 읽는 구성을 다뤘다.
- 콘솔 프로듀서에 입력하는 한 줄은 메시지 한 개다. JSONL 파일도 한 줄씩 보내면 한 줄이 메시지 하나가 된다.
- 컨슈머는 현재 쌓인 메시지를 다 읽어도 새로운 메시지를 기다릴 수 있다. `--max-messages`, `--timeout-ms`, Ctrl+C처럼 종료 조건을 구분한다.
- 이번 구성은 `./data`를 컨테이너의 `/data`에 읽기 전용으로 연결한다. Windows 원본 경로와 컨테이너 안 경로가 같은 파일을 가리키는 방식을 확인한다.
- 토픽 목록·오프셋을 확인하는 명령은 입력한 토픽 이름이 맞는지 검산하는 수단이다. 실제 전송 횟수에 따라 메시지 수가 달라질 수 있다.

## STEP 04 — 파티션 · 키 · 오프셋

- 하나의 토픽을 여러 파티션으로 나누며, 오프셋은 각 파티션 안의 위치다. 메시지 위치를 구분할 때는 토픽·파티션·오프셋을 함께 본다.
- 카드 번호를 키로 보내면 같은 분할 규칙과 파티션 수에서 같은 카드의 사건을 같은 파티션으로 모을 수 있다. 순서는 파티션 안에서 이해하며, 서로 다른 파티션을 읽은 전체 순서와 구분한다.
- 파티션을 늘렸다고 기존 메시지가 새 파티션으로 다시 배치되는 것은 아니다. 키 배정이 바뀔 수 있으므로 파티션 수 변경과 순서의 관계를 살펴본다.
- 콘솔의 `키:값` 입력은 설정한 구분자를 기준으로 나눈다. 카드 키와 JSON 값을 함께 보낼 때 `tags_mini_keyed.txt`를 사용한다.

## STEP 05 — 컨슈머 그룹과 읽던 위치

- 같은 그룹의 컨슈머들은 파티션을 나누어 맡고, 다른 그룹은 각자의 읽던 위치를 관리한다. 누가 어디까지 읽었는지는 메시지 자체와 별개의 상태다.
- `CURRENT-OFFSET`, `LOG-END-OFFSET`, `LAG`를 비교해 그룹이 처리한 위치와 남은 범위를 확인하는 실습이다.
- 이미 커밋한 위치가 있는 그룹은 다시 시작해도 그 위치를 기준으로 이어 읽는다. 처음부터 읽는 옵션을 주었다는 사실만으로 기존 커밋 위치가 초기화되지는 않는다.
- 오프셋 재설정은 먼저 `--dry-run`으로 계획을 보고 `--execute`로 적용하는 흐름이다. 메시지를 지우는 작업과 읽을 위치를 옮겨 재처리하는 작업을 구분한다.

## STEP 06 — Python 프로듀서

- `NewTopic("mini", num_partitions=3, replication_factor=1)`으로 토픽을 생성하고, 반환된 Future의 `.result()`로 요청 결과를 확인하는 코드를 작성했다.
- `Producer`의 `produce()`로 메시지를 전송 대기열에 넣고 `flush()`로 남은 전송을 기다렸다. `len(p)`로 대기열 크기를 비교하는 1,000건 전송 실험도 작성했다.
- 파이썬 딕셔너리는 `json.dumps()`로 JSON 문자열로 바꾸어 보내며, 이미 JSON 문자열인 파일 줄은 그대로 값으로 사용할 수 있다. 카드 번호는 `key`, 사건 JSON은 `value`로 전달한다.
- `on_delivery=report` 콜백에서 성공·실패와 메시지의 파티션·오프셋을 확인한다. `produce()` 호출 시점과 전달 보고가 처리되는 시점을 구분한다.
- `get_watermark_offsets()`의 `lo`, `hi`는 파티션의 시작·끝 오프셋이다. 이 실습의 일반 토픽에서 두 값의 차이로 저장된 범위를 확인한다. 이는 시간 창 집계에서 배울 이벤트 시간 워터마크와 다른 개념이다.

## STEP 07 — Python 컨슈머 · 수동 커밋 · pandas 확인

- `Consumer`에 접속 주소·그룹 이름·초기 위치 설정을 주고 `subscribe(["mini"])`로 토픽을 구독했다.
- `poll(1.0)`을 반복하며 메시지를 받는다. 반환값이 `None`이면 바로 `.value()`를 호출하지 않고 대기·종료 조건을 처리한다. 현재 전체 읽기 반복문은 다섯 번 연속 메시지가 없으면 끝난다.
- 받은 값은 `json.loads(m.value())`로 해석하고, 키는 `.decode()`로 문자열로 바꾼다. 메시지의 파티션·오프셋도 함께 출력해 데이터와 저장 위치를 연결한다.
- `auto.offset.reset="earliest"`는 유효한 커밋 위치가 없는 경우의 시작 정책이다. 이미 읽던 그룹을 무조건 처음으로 되돌리는 설정으로 이해하면 안 된다.
- `enable.auto.commit=False`로 자동 커밋을 끄고 다섯 메시지를 읽은 뒤 `commit(asynchronous=False)`로 읽던 위치를 저장하는 코드를 작성했다. 커밋하지 않고 닫은 경우와 비교해 재수신·중복 처리의 원인을 살핀다.
- `read_all()`을 07-6에 함수로 작성해 재사용했다. 받은 JSON을 pandas DataFrame으로 만들고 승하차별 행 수와 고유 사건 번호 수를 구하는 07-8도 작성했다.

원본 `tags_mini.jsonl`을 이번 정리에서 직접 읽어 확인한 값:

| 항목 | 값 |
|---|---|
| 전체 행 수 | 12행 |
| 승차 / 하차 | 6행 / 6행 |
| 고유 `event_id` | 11개 |

`M07`이 재전송되어 행 수와 사건 번호 가짓수가 다르다. 이 값은 원천 파일에서 확인한 값이며, 현재 Kafka 토픽의 저장량을 조회한 결과는 아니다. 같은 파일을 추가 전송하거나 그룹을 재사용하면 실제 수신 건수는 달라질 수 있다.

## 복습 포인트 (내 코드에서)

- **06-5 — 오프셋 변수 오타:** 현재 출력은 `hi - 10`으로 되어 있다. 숫자 10이 아니라 시작 위치 변수 `lo`를 사용해 `hi - lo`를 계산해야 한다. 원본 코드는 보존하고 복습 항목으로 남겼다.
- **07-1·07-7·07-8 — 그룹 이름:** 문제의 `g07`, `g07x`, `g07p` 대신 각각 `g08`, `g07c`, `g07pp`를 사용하고 있다. 다른 이름 자체가 오류는 아니지만 같은 그룹 재시작과 새 그룹 시작을 비교할 때 이름·커밋 상태를 맞춰야 한다. `g08`이라는 이름을 썼다는 이유로 STEP 08을 진행했다고 판정하지 않는다.
- **07-3·07-4 — 미작성:** 같은 그룹 재시작, 새 그룹의 earliest/latest 비교 셀이 비어 있다. 함수는 07-6에 있으므로 파일의 작성 위치와 문제 번호를 구분한다.
- **07-5·07-6 — 기대 건수의 전제:** 정답의 처리 5건·이어서 7건은 토픽에 12건이 있고 해당 그룹의 이전 커밋 상태가 실험과 맞을 때의 예시다. 그룹을 재사용하면서 항상 같은 수가 나올 것이라고 가정하지 않는다.
- **남은 오류·변형 실습:** 02-6·02-7, 06-4의 키 없는 전송 변형·06-7, 07-4의 그룹 이름 생략 변형·07-9·07-10은 공란이다.
- **재실행 범위:** 프로듀서의 전송 셀을 다시 누르면 메시지가 더 쌓일 수 있고, 초기화 셀은 토픽을 삭제한다. 복습할 때 전체 파일을 한 번에 실행하기보다 필요한 셀과 현재 상태를 확인한다.

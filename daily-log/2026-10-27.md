## STEP 08 — 키 선택 · 분할 규칙 · 데이터 쏠림

- 같은 카드 키를 Python 기본 프로듀서와 `partitioner="murmur2_random"` 프로듀서로 보내 분할 결과를 비교하는 코드를 작성했다. 같은 키라도 사용하는 분할 규칙이 다르면 파티션이 달라질 수 있어, 다른 클라이언트와 규칙을 맞추는 것이 중요하다.
- 키 없는 전송 변형에서는 전달 보고로 실제 배정된 파티션을 모았다. 키가 없을 때의 분배와 키가 있을 때의 해시 분배를 구분한다.
- `counts(topic)`은 토픽의 파티션 목록을 구하고 각 파티션의 `hi - lo`를 리스트로 반환한다. STEP 06의 오프셋 범위 조회를 함수로 재사용한 것이다.
- 같은 하루 로그를 `by_card`에는 카드 번호 키로, `by_station`에는 역 코드 키로 보냈다. 합계가 같아도 키의 가짓수·분포에 따라 파티션별 부하가 달라진다.
- `probe3` 토픽에 역마다 메시지 하나를 보내 역 코드가 어떤 파티션으로 가는지 확인하는 코드를 작성했다. `{rec["station_id"] for rec in day}`는 역 코드 중복을 없애는 집합(set), `st_part = {}`는 역 코드와 파티션을 연결할 사전(dict)이다.
- 파티션 6개짜리 토픽에서도 카드 키와 역 키를 비교했다. 파티션을 늘려도 키가 적거나 해시 배치가 치우치면 빈 파티션과 바쁜 파티션이 생길 수 있다. STEP 14 Spark 실습에서 다룬 쏠림과 연결되는 개념이다.

## STEP 09 — JSONL 재생기와 세 종류의 시각

- `send_file(path, topic)`은 파일의 빈 줄을 건너뛰고, 카드 번호를 키로 JSON 한 줄씩 전송하며 전송한 행 수를 반환한다. 마지막 `flush()`로 대기 중 전송을 기다린다.
- `replay(path, topic, speed)`는 연속한 `recv_time` 차이를 `speed`로 나누어 기다리며 원천의 도착 간격을 빠르게 재현한다. 설정한 배속 외에도 파일 해석·전송 대기·실행 환경의 비용이 전체 시간에 영향을 준다.
- 현재 09-4의 호출 배속은 6000이다. 별도의 600 대 6000 비교 셀은 비어 있어 두 조건의 실제 측정 결과는 저장된 코드만으로 확인되지 않는다.
- Kafka 메시지의 `timestamp`, 데이터의 실제 사건 시각 `tag_time`, 원천 도착 시각 `recv_time`을 나란히 출력했다. 과거 데이터를 오늘 재생해도 데이터 안의 사건 시각은 과거로 남으므로 각 시각의 용도를 구분한다.
- `tools.replay.send_part(2)`로 다음 조각을 보내고 `counts()`의 합계를 보는 코드를 작성했다. 같은 전송 셀을 반복하면 메시지가 추가되므로 파일 행 수와 현재 토픽 저장량을 자동으로 같다고 가정하지 않는다.

## STEP 12 — Kafka 메시지를 Spark DataFrame으로 읽기

- `spark.read.format("kafka")`에 접속 주소·구독 토픽·시작 오프셋을 주어 배치로 읽었다. 메시지의 `key`, `value`뿐 아니라 `topic`, `partition`, `offset`, Kafka 시각 등 메타데이터가 함께 들어온다.
- 원시 `key`와 `value`는 바이너리다. `.cast("string")`으로 문자열로 읽고, `from_json(..., SCHEMA)`로 JSON을 구조화한 뒤 `select("e.*", "partition", "offset")`으로 펼쳤다.
- 원천 사건 번호와 Kafka의 파티션·오프셋을 함께 남기면 사건의 업무 식별자와 전달 위치를 구분해 추적할 수 있다.
- 승하차 건수·고유 사건 수·파티션별 행 수를 구하고, 시각 NULL 조회와 임시 뷰의 SQL 집계도 작성했다. 입력이 파일에서 Kafka로 바뀌어도 표로 변환한 뒤의 집계 방법은 연결된다.

원천 `tags_day.jsonl`을 이번 정리에서 직접 읽어 확인한 비교 기준이다. 현재 Kafka 토픽이나 Spark 쿼리의 실행 결과를 조회한 값은 아니다.

|---|---|
| 전체 태그 행 | 2,008행 |
| 승차 / 하차 | 1,012행 / 996행 |
| 서로 다른 `event_id` | 1,988개 |

## STEP 13 — 스트리밍 시간 창 · 워터마크 · 체크포인트

- `read`를 `readStream`으로 바꾸고 Kafka 메시지를 파싱해 스트리밍 DataFrame `live`를 만드는 코드를 작성했다. DataFrame 정의와 실제 스트리밍 쿼리의 시작은 별개다.
- 13-5의 `run_win()`은 사건 시각에 10분 워터마크를 두고 5분 창으로 집계해 Parquet에 `append`하는 함수다. `availableNow=True`로 현재 처리할 수 있는 입력을 처리한 뒤 종료하도록 구성했다.
- `checkpointLocation`은 처리 위치와 스트리밍 상태를 이어 가기 위한 경로다. 같은 체크포인트로 재시작할 때는 처음의 `startingOffsets` 설정과 체크포인트의 재개 위치를 구분한다.
- 워터마크는 관측한 이벤트 시간의 진행과 지연 허용 범위에 관련되며, 단순히 PC에서 10분 기다리는 타이머가 아니다. 닫힌 창만 내보내는 append 집계에서는 입력 처리 종료가 모든 창의 마감을 뜻하지 않는다.
- `recentProgress`·`lastProgress`에서 입력 행 수, 이벤트 시간 워터마크, 늦어서 버린 행 수를 살펴보는 코드를 작성했다. `show_win()`은 저장된 창 개수와 그 안의 태그 합계를 확인하는 함수다.
- 13-2~13-4와 13-6 이후 호출·비교 셀이 비어 있어, 메모리 집계나 조각별 워터마크 변화를 실제로 비교 완료했다고 기록하지 않는다.

## STEP 14 — 집계 결과를 Kafka에 다시 쓰기

- `tags`를 배치로 읽어 사건 번호 중복을 제거한 뒤 역별 승차 수 `boards`를 만들었다. 이번 집계는 미등록 역 S99나 깨진 시각을 별도로 격리하지 않으므로 앞선 Spark 과목의 `clean` 기준과 구분한다.
- `struct()`로 여러 열을 묶고 `to_json()`으로 직렬화해 Kafka 전송용 `key`, `value` 열을 만들었다. 이는 읽을 때 사용한 `from_json()`과 반대 방향의 변환이다.
- 역 마스터를 left join해 JSON에 역 이름을 포함하는 변형도 작성했다. 마스터에 없는 역이 결과에서 유지되는지 확인할 수 있는 구성이다.
- `out.write.format("kafka")`로 `station_cnt`에 저장하고 다시 읽어 key·value를 문자열로 보는 코드를 작성했다.
- 14-5는 승차 이벤트를 5분 창으로 묶어 `win5` 토픽에 보내는 쿼리다. `outputMode("update")`는 바뀐 집계값을 창 마감 전에도 내보낼 수 있어 같은 키의 갱신 메시지가 여러 번 생길 수 있다. 후속 저장소에서 최신값으로 처리할 기준이 필요하다.
- 정답의 역별 결과 9행과 `win5` 36행은 정답의 전송·초기화 조건에서 나온 예시다. 현재 `tags_live`에 모든 조각이 들어갔는지 확인하지 않았으므로 내 결과로 기록하지 않는다.

## 복습 포인트 (내 코드에서)

- **08-1·08-2 — 토픽 이름:** 문제의 `tags3` 대신 `tag3`로 보내고 개수를 조회한다. 키 없는 전송 변형은 `tags3`를 사용하므로 서로 다른 토픽의 결과를 섞어 비교할 수 있다. 비교할 토픽과 파티션 수를 통일해야 한다.
- **08-4 — set과 dict 구분:** 역 코드를 한 번씩 보내는 집합 표현식과, 전송 결과를 저장하는 `st_part` 사전의 역할을 구분한다. 주석의 set 설명을 `st_part = {}`의 자료형 설명으로 읽지 않는다.
- **09-4 — 배속과 None:** 현재 기본 호출이 6000이므로 제목의 600배 실험과 다르다. `prev is None`은 첫 메시지라 이전 시각이 없다는 초기 상태이며, 잘못된 시각을 자동으로 처리하는 기능은 아니다. 문자열 해석 오류는 별도로 발생할 수 있다.
- **12-7 — 자료형 설명:** value를 문자열로 캐스팅한 뒤에도 `from_json`은 `SCHEMA`에 따라 `tag_time`을 Timestamp로 해석한다. 현재 주석의 '스트링이라 값이 있다'는 설명과 실제 스키마를 구분하고, `ev.printSchema()`와 원문·NULL 결과를 함께 확인한다.
- **13-1 — 시작 위치 오타:** `startingOffsets` 값이 `"ealiest"`로 적혀 있다. 의도한 `"earliest"`와 달라 실행 전 수정이 필요하다. 파이썬 문법 검사는 이런 옵션 값의 오류를 잡지 못한다.
- **14-3 — 조회 토픽 오타:** `station_cnt`에 쓴 다음 `counts("staiton_cnt")`를 호출하고 있다. 전송 대상과 확인 대상의 철자를 맞춘다.
- **14-5 — 입력량 전제:** 문제 설명은 10조각 전송을 전제로 하지만 현재 13-7·13-8의 전송 반복 셀은 비어 있다. 결과를 정답과 비교하기 전에 실제 전송 범위와 체크포인트 재사용 여부를 확인한다.

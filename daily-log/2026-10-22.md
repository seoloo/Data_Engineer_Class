## STEP 11 — Spark SQL

- `df.createOrReplaceTempView("tags")`로 DataFrame에 이름을 붙이면 `spark.sql("SELECT ... FROM tags")`로 질의할 수 있다.
- 같은 질문을 SQL과 DataFrame 함수(`filter → join → groupBy → agg → orderBy`)로 각각 써도 결과는 같다. 둘을 섞어 쓸 수도 있다. 예: SQL 결과에 `F.sum("cnt").over(Window.partitionBy())`로 비율 칸을 붙이기.
- `HOUR(tag_time)`, `COUNT(DISTINCT event_id)`, CTE(`WITH board AS (...)`)와 서브쿼리로 평균보다 많은 역만 고르기.
- 없는 표 이름을 쓰면 `TABLE_OR_VIEW_NOT_FOUND` 오류가 난다. Interactive 창을 새로 열었다면 뷰 이름도 다시 붙여야 한다.
- 결과가 작을 때만 `.toPandas()`로 꺼낸다.

## STEP 12 — 시간 창 (Tumbling / Sliding)

- `F.window("tag_time", "5 minutes")`: 겹치지 않는 Tumbling 창이다. 각 이벤트가 창 하나에만 들어가서, 창별 count를 더하면 전체 건수와 같다.
- `F.window("tag_time", "10 minutes", "5 minutes")`: 10분 창을 5분씩 미는 Sliding 창이다. 이벤트가 창 두 개(창 길이 ÷ 미는 간격)에 들어가서 합계가 전체 건수의 2배가 된다.
- 창은 struct 타입이라 `w.start`, `w.end`로 펼쳐서 본다.
- 1시간 Tumbling 창의 결과는 STEP 09의 `date_trunc("hour", ...)` 결과와 같다.
- **이벤트 시간(`tag_time`)과 도착 시간(`recv_time`)을 구분해야 한다.** 늦게 도착한 기록을 도착 시간으로 세면 엉뚱한 창에 들어간다 (07:30 창 기준 16건 vs 14건). 스트리밍의 watermark로 이어지는 개념이다.

## STEP 13 — 중복 제거 · 격리 · 승하차 짝 맞추기

- `dropDuplicates(["event_id"])`: 키 기준으로 중복을 제거한다. 원본 2008줄에서 1988줄이 남는다.
- 칸 목록 없이 `dropDuplicates()`를 쓰면 모든 칸이 같은 줄만 지운다. 키를 잘못 고르면(`card_id`) 정상 데이터까지 날아간다.
- 역 코드가 비었거나 등록되지 않은 역이거나 시각이 비어 있으면 `is_bad` 조건으로 격리한다. `quarantine`에는 `when(...).otherwise(...)`로 `UNKNOWN_STATION` 또는 `BAD_TIME` 사유를 붙이고, `~is_bad`인 행은 `clean`으로 남긴다.
- `원본 = 중복 + 격리 + 정상`을 검산한다. 정답 기준 `2008 = 20 + 10 + 1978`로, 처리 과정에서 행이 빠지지 않았는지 확인하는 기준이다.
- 승차와 하차를 각각 `board`, `alight`로 만들고 `trip_id`로 left join한다. 승차를 기준으로 하므로 아직 하차가 없는 이동도 남는다. 반대로 승차가 없는 하차는 `left_anti`로 따로 찾는다.
- `unix_timestamp(하차) - unix_timestamp(승차)`를 60으로 나누어 이동 시간(분)을 구한다. 하차가 없는 행의 이동 시간은 NULL이며 평균·최소·최대 집계에서 빠진다.
- 원본과 정상 데이터의 역별 승차 수를 나란히 비교한다. 같은 질문도 중복·격리 처리 전후에 따라 답이 달라지므로 집계에 사용한 데이터 단계를 명시한다.

정답 파일에 기록된 비교 기준:

| 항목 | 기대값 |
|---|---|
| 격리 사유 | `UNKNOWN_STATION` 6건, `BAD_TIME` 4건 |
| 이동 수 / 하차가 없는 이동 | 992건 / 14건 |
| 승차가 없는 하차 | 8건 |
| 이동 시간 평균 / 최소 / 최대 | 27.1분 / 8.0분 / 46.0분 |
| 정상 승차 / 정상 하차 / 요금 합계 | 992건 / 986건 / 1,647,800원 |

## STEP 14 — 파티션 · 셔플 · AQE · 캐시

- `rdd.getNumPartitions()`로 조각 수를 보고, 작은 실습 데이터에서 `glom().map(len).collect()`로 조각별 행 수를 확인한다.
- `repartition(4)`는 셔플로 데이터를 다시 나눈다. `coalesce(1)`은 셔플 없이 조각 수를 줄일 때 사용하며, 결과를 한 조각에 모으면 병렬성이 줄어든다.
- `repartition(4, "station_id")`처럼 키를 지정하면 같은 키가 같은 조각으로 모인다. 키 분포에 따라 쏠림(skew)이 생기며, `tag_type`처럼 값이 두 가지인 키로 나누면 데이터가 들어가는 조각도 최대 두 개다.
- `explain()`의 `Exchange`는 셔플을 확인하는 단서다. `dropDuplicates()`는 이벤트 키끼리, `groupBy()`는 집계 키끼리 모아야 하므로 실행 계획에 셔플이 나타난다.
- `spark.sql.shuffle.partitions`로 셔플 조각 수를 설정하고, `spark.sql.adaptive.enabled`로 AQE(적응형 쿼리 실행)를 확인한다. AQE는 실행 중 통계를 이용해 계획을 조정한다.
- `cache()` 후 첫 `count()`로 캐시를 채우고 다시 사용한다. Spark UI의 Storage 탭은 캐시, Stages 탭은 Shuffle Read·Write를 확인하는 데 사용한다. UI 확인 여부는 저장된 코드만으로는 판정하지 않았다.
- 시간 비교 실습에서는 AQE를 잠시 끄고 같은 집계를 반복한다. 조각이 많으면 작은 데이터에서는 작업 관리 비용이 커질 수 있다. 실행 시간은 PC와 캐시·설정에 따라 달라지므로 실제 측정값으로 비교한다.
- 실험이 끝나면 `unpersist()`로 캐시를 풀고 AQE와 셔플 조각 수를 되돌린다.

## 복습 포인트 (내 코드에서)

- **13-1 — 수정됨:** 최종 원본에는 `raw.select("event_id").distinct().count()`가 들어갔고, 전체 행 수와의 차이도 계산한다. 오전 기록의 `distinct()` 누락은 해결된 상태다.
- **13-9 — 최대값 함수:** `F.min("travel_min").alias("max")`로 되어 있다. 열 이름만 `max`이고 실제로는 최소값을 구하므로 `F.max("travel_min")`으로 고쳐야 한다.
- **14-9 — 비교 조건과 표시:** 출력 문구는 "200 조각"인데 호출은 `run(300)`이다. 문제의 200 대 8 비교를 하려면 `run(200)`으로 맞추고, 300을 실험한 것이라면 출력 문구를 맞춘다.
- **14-11 — 설정 이름:** `spark.sql.partitions`로 설정하고 있다. 되돌려야 할 키는 `spark.sql.shuffle.partitions`이며, 현재 코드는 의도한 셔플 설정을 200으로 복원하지 못한다.
- **12-9:** `count_at` 안에서 `.show()`를 호출하면 반환값이 `None`이라 `print(..., None)`이 찍힌다. 숫자로 비교하려면 `.first()["count"]`를 반환해야 한다.
- **12-5 — 조회 범위:** 문제는 08:00~08:30이지만 현재 코드는 08:50 미만까지 조회한다. 조건을 바꿔 본 것인지 확인하고 비교할 때 범위를 통일한다.
- **출력 행 수:** 11-10은 `.toPandas()` 뒤의 `.head(3)`이 빠져 있고, 14-10은 `.show()`라 기본 20행을 표시한다. 문제의 상위 세 줄만 보려면 각각 `.head(3)`, `.show(3)`을 사용한다.
- **11-9:** 일부러 틀려 보는 셀(`tagz`)을 비워 두었다. 오류 메시지를 한 번 직접 보면 좋다.
- **13-13 — 미작성:** NULL 역 코드가 `isin()`을 만났을 때의 동작을 확인하는 셀이 비어 있다. `isNull()`이 없으면 조건과 그 부정이 모두 NULL이 되어, 해당 행이 정상과 격리 어느 쪽에도 들어가지 않을 수 있다.

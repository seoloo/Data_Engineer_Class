[10-2] 3대짜리를 띄우십시오.

[10-4] kafka-1 안으로 들어가십시오.
[어디서] PowerShell (VS Code 아래 터미널, C:\kafkacamp)
--------------------------------------------------------------------------------
docker exec -it kafka-1 bash

── 결과 (학생 PC 화면 — 아이디·시각은 PC 마다 다름) ──
kafka-1:/opt/kafka/bin$

→ 이 STEP 의 Kafka 명령은 --bootstrap-server kafka-1:19092 를 씁니다. 컨테이너끼리 부르는 이름(kafka-1)과
문(19092)입니다 — localhost:9092 로 물으면 다른 브로커의 주소를 localhost:9093 처럼 알려 주는데, 그 주소는 컨테이너 안에서는
없는 곳이기 때문입니다.

[10-5] 복제 3짜리 토픽 두 개를 만드십시오 — tags_rf3(min.insync.replicas=2) 와 strict3(min.insync.replicas=3).
[어디서] kafka-1 컨테이너 안 (docker exec -it kafka-1 bash)
--------------------------------------------------------------------------------
./kafka-topics.sh --bootstrap-server kafka-1:19092 --create --topic tags_rf3 --partitions 3 --replication-factor 3 --config min.insync.replicas=2
./kafka-topics.sh --bootstrap-server kafka-1:19092 --create --topic strict3 --partitions 1 --replication-factor 3 --config min.insync.replicas=3

── 결과 (Kafka 4.3.1 화면) ──
Created topic tags_rf3.
Created topic strict3.

→ --replication-factor 3 = 장부마다 복사본 셋. --config 는 이 토픽만의 설정을 붙입니다.

[10-10] 2번이 꺼진 채로 두 줄을 더 보내고, 처음부터 전부 읽으십시오.
[어디서] kafka-1 컨테이너 안 (docker exec -it kafka-1 bash)
--------------------------------------------------------------------------------
./kafka-console-producer.sh --bootstrap-server kafka-1:19092 --topic tags_rf3 --reader-property parse.key=true --reader-property key.separator=:
>C001:OUT S03
>C002:OUT S01
>(Ctrl+C)
./kafka-console-consumer.sh --bootstrap-server kafka-1:19092 --topic tags_rf3 --from-beginning --formatter-property print.key=true --timeout-ms 5000

── 결과 (Kafka 4.3.1 화면 — 리더가 몇 번 브로커인지는 PC 마다 다를 수 있음) ──
The consumer rebalance protocol (KIP-848) is production-ready! Set group.protocol=consumer to try it out. See https://kafka.apache.org/documentation/#consumer_rebalance_protocol
C002	IN S06
C002	OUT S01
C001	IN S01
C003	IN S03
C001	OUT S03
Processed a total of 5 messages

→ 5줄 전부 — 장애 전에 쓴 3줄도, 장애 중에 쓴 2줄도. ISR 이 두 곳(1 · 3)이라 min.insync.replicas=2 를 채우므로 쓰기도
됩니다. 이것이 "한 대가 죽어도 서비스는 계속된다" 입니다. (파티션별로 묶여 나오는 순서는 PC 마다 다를 수 있음)

[10-11] min.insync.replicas=3 인 strict3 에 한 줄 보내 보십시오. 몇 초 지켜본 뒤 Ctrl+C.
[어디서] kafka-1 컨테이너 안 (docker exec -it kafka-1 bash)
--------------------------------------------------------------------------------
./kafka-console-producer.sh --bootstrap-server kafka-1:19092 --topic strict3
>will this be saved?
>(Ctrl+C)

── 결과 (Kafka 4.3.1 화면 — 시각·번호는 다름, 같은 WARN 이 계속 이어짐) ──
[2026-10-16 10:21:07,412] WARN [Producer clientId=console-producer] Got error produce response with correlation id 6 on topic-partition strict3-0, retrying (2147483646 attempts left). Error: NOT_ENOUGH_REPLICAS (org.apache.kafka.clients.producer.internals.Sender)
[2026-10-16 10:21:07,515] WARN [Producer clientId=console-producer] Got error produce response with correlation id 7 on topic-partition strict3-0, retrying (2147483645 attempts left). Error: NOT_ENOUGH_REPLICAS (org.apache.kafka.clients.producer.internals.Sender)
...

→ NOT_ENOUGH_REPLICAS — "최소 3곳에 적어야 하는데 지금 살아 있는 복사본이 2곳뿐". 프로듀서는 포기하지 않고 계속 다시
시도합니다(attempts left 가 줄어드는 것). Kafka 는 약속(3곳)을 못 지키면 '완료' 라고 말하지 않습니다. 데이터를 잃느니 멈추는 쪽을 고른
것입니다.

[10-11 바꿔 보기 ①] 같은 strict3 에 acks=1 로 보내면?
./kafka-console-producer.sh --bootstrap-server kafka-1:19092 --topic strict3 --command-property acks=1
>saved with acks=1?
>(Ctrl+C)
./kafka-console-consumer.sh --bootstrap-server kafka-1:19092 --topic strict3 --from-beginning --timeout-ms 5000

── 결과 ──
The consumer rebalance protocol (KIP-848) is production-ready! Set group.protocol=consumer to try it out. See https://kafka.apache.org/documentation/#consumer_rebalance_protocol
saved with acks=1?
Processed a total of 1 messages

→ 이래서 — WARN 없이 저장되고, 읽으면 나옵니다. acks=1 은 "리더 한 곳에만 적히면 영수증을 달라" 라서 min.insync.replicas 를
검사하지 않습니다. 빠르지만, 그 순간 리더가 죽으면 이 메시지는 사라질 수 있습니다. 그래서 잃으면 안 되는 데이터(결제 · 정산)는 acks=all, 조금
잃어도 되는 데이터(화면 클릭 로그)는 acks=1 로 고르기도 합니다 — 속도와 안전의 맞바꿈입니다.
